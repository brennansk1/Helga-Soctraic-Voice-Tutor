# CONTAINER path — the portable fallback (TTS_BACKEND=torch).
#
# Kokoro-82M has two runtimes and this project uses both, in two different
# places. See README.md.
#
#   HOST (default, Apple Silicon):  TTS_BACKEND=mlx    -> requirements-host.txt
#   CONTAINER (this file, fallback): TTS_BACKEND=torch -> kokoro (PyTorch)
#
# mlx-audio is deliberately NOT here. MLX publishes a manylinux aarch64 wheel,
# so `pip install` succeeds and the image looks configured — but there is no
# Metal inside a Linux container on macOS, so it would run on virtualised CPU
# or fail at load. This file previously declared mlx-audio with `kokoro`
# commented out, which left the container with no working backend at all: the
# health check passed and the first synthesis request raised
# "no TTS backend available".
